# B20: User specification as the audit yardstick
Type: planner
Size: L

## Goal
Teams already have a tracking plan or a requirements list ("purchase must carry transaction_id, value, currency and items", "no hit before consent", "generate_lead on the contact form submit"). They should be able to add it once per site, and the audit should check the session against **their** requirements one by one: pass, fail, or not tested on this journey. Today the yardstick is only the LLM-generated journey plan (`JourneyPlan`) or the built-in rules.

## Acceptance criteria
- [ ] A user can add a specification for a site in Settings or the popup:
  - paste free text or Markdown (one requirement per line or bullet), or
  - upload CSV/JSON in a documented format (columns: id, requirement, event, params, page type, severity).
  It's stored locally per site (domain) and can be edited, replaced and deleted.
- [ ] Each requirement is turned into a structured form: `id` (REQ-1… or the user's own id), the original text, `scope` (event and/or page type), checkable parts (event present, params present, value type or allowed values, ordering, consent state) and severity.
  - CSV/JSON maps directly.
  - Free text is converted by the user's LLM with a new prompt and JSON schema (same validator and retry as the planner). The user sees the converted list and confirms it before it's saved.
- [ ] A requirement that can't be made checkable is kept as "LLM-judged". It's never silently dropped.
- [ ] At audit time:
  - the deterministic parts are checked by a new rules pass;
  - the LLM-judged parts go into the audit payload as `specification`;
  - the report gets a "Your specification" section listing every requirement as pass / fail / not tested with evidence event IDs. "Not tested" means the journey didn't reach the scope.
- [ ] The confirmed specification takes precedence over the generated journey plan where they overlap, and the report says which one was used.
- [ ] Nothing from the specification is sent anywhere except the user's own LLM provider, and only after the existing consent step.
- [ ] Unit tests cover:
  - CSV/JSON parsing and validation errors shown to the user;
  - the free-text conversion schema with a mocked LLM;
  - each deterministic check type;
  - pass/fail/not-tested on fixture sessions.
  The eval gets a fixture with a specification and seeded violations.
- [ ] `npm run typecheck && npm test && npm run build && npm run e2e` pass, and `npm run eval -- --mock` still passes.

## Out of scope
- Syncing specifications with external tools (Google Sheets, Avo, Amplitude Data, …).
- Sharing specifications between users.
