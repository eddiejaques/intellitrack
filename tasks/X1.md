# X1: Site context during recording + page-aware audit
Type: feature
Size: M

## Goal
The audit should know what kind of site and page it is looking at, and why the user was there, without the user having to build a plan first. For example, a normal content or home page shouldn't be faulted for missing product or e-commerce fields. Today the page context (`extractPageContext`) is only grabbed when the user asks the LLM for a journey plan, and the audit never sees it.

## Acceptance criteria
- [ ] While recording, the page context is captured automatically on every distinct page of the recorded tabs, after load and after SPA URL changes (debounced), and stored on the session with the page's path. It still collects structure only (no form values, no query strings, no cookies), as `extractPageContext` does today.
- [ ] The context is extended with:
  - `page_type`: one of home, listing, product, cart, checkout, confirmation, content, lead_form, account, search, other. It's decided by a pure, unit-tested function from the URL path, schema.org types, og:type and page elements (price, add-to-cart button, forms and their field types, article markup).
  - `site_signals`: which tag managers and IDs are loaded (`GTM-`, `G-`, `AW-`, from the existing `tag_loads`), whether a consent banner/CMP is present (OneTrust, Cookiebot, Usercentrics, Didomi, Quantcast, or a generic cookie-banner heuristic), and the platform if visible (Shopify, WooCommerce, Magento, …).
- [ ] The session's site type (ecommerce, lead_generation, content, other) is inferred from the collected pages, and used when there's no confirmed plan.
- [ ] The audit payload includes a `site` block (site type + why) and per-page `page_type`, so every event can be tied to the page type it fired on.
- [ ] Rules: e-commerce parameter checks (items/value/currency) only apply to events on product, listing, cart, checkout and confirmation pages, or to e-commerce events wherever they fire. A home or content page with only page_view/scroll/engagement produces no e-commerce finding.
- [ ] The audit prompt (`shared/prompts/audit_v1.md`) tells the LLM to judge each event against its page type and the site's purpose, and not to expect product or e-commerce fields on non-commerce pages.
- [ ] The popup or live panel shows the detected site type and current page type, e.g. "Shop · product page".
- [ ] Unit tests: page-type classification on fixtures for each type; e-commerce rules silent on a content-page session and still firing on a product page; payload contains `site` and `page_type`.
- [ ] `npm run e2e` gets a check that the cart and product test pages are classified cart and product, and home as home.
- [ ] `npm run typecheck && npm test && npm run build && npm run e2e` pass, and `npm run eval -- --mock` still passes.

## Out of scope
- Sending page HTML or screenshots to the LLM.
- Changing the journey planner (it can reuse the new context later).
